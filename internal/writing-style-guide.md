# 公开文档文本风格规范

> 用途：统一公开文档站的语言风格、结构排版与术语口径，兼顾技术专业性、易读性与规范性
>
> 使用范围：`docs/**/*.md`
>
> 发布规则：本文件仅供仓库内部编写与审校使用，不作为公开页面发布

本规范与仓库根目录 `AGENTS.md`、`internal/component-document-template.md`、`internal/standard-document-template.md` 配套使用。**本规范只约束表达与排版，不改变任何既定技术选型、架构层级与路由规则。**

## 定位与目标语调

本站定位为**面向数万人规模企业与全私有化环境的架构蓝图与选型规范文档站**，核心受众包括管理层与决策者、架构师、安全与治理团队、实施与运维团队。

公开文档统一遵循以下语调基准：

- **技术保真（首要原则）**：任何润色不得缩减、模糊或改写既定的组件型号、协议版本、职责边界与采用规则。
- **专业克制**：使用精准的工程书面语，不堆砌营销形容词，也不保留随笔式口语。
- **结论先行**：核心定位、边界红线与关键结论前置呈现，便于跳跃式扫读。
- **边界清晰**：持续保留本项目最核心的优势——明确说明每个层级、组件与协议“负责什么、不负责什么、不替代什么”。

## 公开内容红线（与 `AGENTS.md` 对齐）

编写或审校公开页面时，必须同时满足以下硬性约束：

1. **禁止擅自修改技术口径**：不得在润色时省略模型完整命名空间（如 `Qwen/Qwen3-Embedding-8B`）、合并或挪动组件职责归属、弱化互斥或条件引入边界。
2. **禁止出现内部迭代版本号**：公开页面标题、导航、卡片、正文与路由中不得出现内部方案版本号或“这一版 / 上一版 / 此前六层”等版本演进痕迹。
3. **禁止在公开正文写维护元话语**：面向作者的编写规则、页面复用说明或参考来源解释只保留在 `AGENTS.md` 和 `internal/`，不得写入公开正文。
4. **保持标题与路由稳定**：首页主标题与站点标题统一为 `企业级智能体开源系统方案`；主方案固定 `/framework`，组件清单固定 `/components`。

## 语言风格：推荐 vs 避免

### 1. 去除内部自指与维护视角

| 避免（内部视角 / 元话语） | 推荐（读者视角 / 结论陈述） |
| --- | --- |
| `此前“六层”只适合作为抽象归并，不再作为公开表达。` | 直接陈述当前九层架构，不提及历史归并口径。 |
| `参考现代开发文档首页的组织方式，这里按……` | `沿“理解 → 设计 → 标准化 → 落地”四个阶段，完成规划与投产。` |
| `复用规则：互斥候选的组件说明页` | `采用定位：主平台路线（三选一互斥候选）` |
| `快速理解这一版到底采用什么组件组合` | `系统了解核心组件组合、职责边界与实施路线。` |
| `公开站点只展示一个当前状态，因此组件、协议和路线都要收敛` | 拆分为架构原则本身：`核心技术路线保持单轨收敛，避免长期并行多套同类主底座。` |

### 2. 去除口语化与文学化表达

| 避免（口语 / 随笔 / 文学词） | 推荐（工程书面语） |
| --- | --- |
| `先把原则定死，否则组件会越堆越乱。` | `以下十项原则用于确立架构约束基线，避免演进中出现组件无序叠加。` |
| `这是这套方案最关键的部分。` | 直接进入正文，或说明关键原因（如“清晰的职责边界是平台长期可演进的前提”）。 |
| `形成可认真生产的最小组合` | `满足部门级生产治理要求的最小组合` |
| `把太多编排逻辑塞进 BFF` | `将复杂编排逻辑过度耦合在 BFF 层` |
| `APISIX 守北向统一入口` | `APISIX 负责北向统一入口` |
| `当前定下来的组件` | `核心选型组件` |

### 3. 避免跨页面长段复读（单一权威出处）

以下高频共性口径只需在**主出处页**完整展开，其他页面统一压缩为一句话结论加内链：

- **主平台三选一收敛规则**：主出处 `docs/stack.md`、`docs/framework.md`。
- **默认门户（`AgentifUI`）与条件引入（`OpenClaw`）边界**：主出处 `docs/layers/portal-application.md`、`docs/components/openclaw.md`。
- **单环境服务器估算口径与企业现有能力复用**：主出处 `docs/deployment.md`。
- **开源许可证口径**：主出处 `docs/open-source-status.md`。

## 结构与扫读排版规范

### 1. 长文开头结论先行（BLUF）

篇幅较长的核心专题页（如 `framework.md`、`architecture.md`、`deployment.md`、`governance.md`），在标题与适用范围之后，建议使用 VitePress `::: info 核心摘要` 容器给出 3~4 条核心结论与关键关联入口，替代一整段密集的纯文字跳转句。

### 2. 列表加粗关键词前缀（Lead-in Bold）

当列表项超过 4 条且每条为完整说明句时，优先提炼 4~8 字的加粗前缀，降低扫读成本：

```markdown
- **最小权限与凭据隔离**：严格收敛凭据与访问范围，禁止将系统级密钥直接暴露给 Agent Runtime。
- **全链路审计留痕**：将工具调用日志、错误码与请求上下文统一纳入观测与审计体系。
```

### 3. 合理使用表格替代重复小节

当连续出现 5 个以上“1 个三级标题 + 1 句话说明”的同构小节（如技术栈总览、组件分工、规模对照）时，优先合并为结构化 Markdown 表格，推荐采用 3 列结构（如 `能力域 | 职责定位 | 选型组件`），避免单列文字过长。

### 4. 善用 VitePress 原生提示容器

- `::: info`：用于页面核心摘要、阅读导航或统计口径说明。
- `::: tip`：用于强调一句话架构口径、最佳实践或推荐路径。
- `::: warning`：用于强调架构红线、严禁绕过的治理约束或高风险操作边界。
- 避免全页过度堆砌容器，单页建议不超过 3 处。

### 5. 标题层级与编号

- 公开页二级标题优先采用**无中文序号**形式（如 `## 方案定位`、`## 设计原则`），由右侧目录（TOC）自然呈现层级；九层架构分册的顶层名称（如 `# 3. 门户与应用层`）保留阿拉伯数字层级编号以体现架构顺序。
- 标题必须名实相符：若卡片按目标划分则写“按目标选择阅读入口”，按角色划分（管理层 / 架构师 / 安全 / 实施）才写“按角色选择”。

## 术语、符号与格式规范

### 1. 行内代码反引号（`` `...` ``）使用规则

- **应该加反引号**：具体开源组件名（`APISIX`、`LiteLLM`、`vLLM`）、完整模型名（`Qwen/Qwen3-Embedding-8B`）、协议与标准缩写（`MCP`、`A2A`、`OpenAPI`、`OIDC`）、环境名与配置项（`dev`、`staging`、`prod`）、路径与命令。
- **不加反引号**：普通中文概念、数量词与规模描述（如写 `1 台`、`2–3 台`、`5 个核心服务`，不写 `` `1 台` ``、`` `5` 个核心服务 ``）；通用行业名词（如 RAG、Agent、BFF、Workflow）在正文中可不加反引号，保持全页一致即可。

### 2. 常用术语中英文口径

| 规范写法 | 避免写法 | 说明 |
| --- | --- | --- |
| `北向` / `南向（Southbound）` | 一边写“北向”，一边裸写 `southbound` | 保持中英文对称；首次出现可附英文括号说明 |
| `Agent Runtime` | 混用小写 `runtime` 与 `Runtime` | 专指运行时概念时统一首字母大写 |
| `数万人规模企业` / `几万人规模企业` | `万人级企业` | 保持原方案体量口径，不擅自缩水 |
| `KMS / 证书体系` | 简写为 `KMS` | 保留完整安全能力项 |
| `Qwen/Qwen3-Embedding-8B` | 省略前缀写 `Qwen3-Embedding-8B` | 涉及具体模型仓库 ID 时保留完整命名空间 |

### 3. 标点与空格

- **中英文混排**：中文与英文单词、数字之间保留一个半角空格（如 `基于 VitePress 构建`、`9 层架构`）；中文标点前后不加空格。
- **流程箭头**：正文中描述阅读阶段或逻辑演进统一使用中文排版箭头 `→`（如 `理解 → 设计 → 标准化 → 落地`）；代码样式或纯文本链路图可统一使用 `→` 或 `->`，同一页面内不混用。
- **列表末句号**：短语型列表（无主谓结构）统一不加句号；完整句子列表统一加句号；同一列表内不混用。

## 审校快速检查清单

修改或提交公开文档前，按以下清单逐项核对：

- [ ] **技术保真（首要）**：组件名、模型完整 ID、协议版本、采用边界（默认 / 条件 / 互斥）是否与主方案完全一致？
- [ ] **合规检查**：是否不含任何内部版本号、历史归并口径与面向作者的维护元话语？
- [ ] **语调检查**：是否已替换所有口语化、随笔化或文学化措辞（如“定死”“塞进”“认真生产”）？
- [ ] **扫读体验**：长文开头是否有核心摘要？长列表是否已加粗关键词前缀？重复单句小节是否适合转为表格？
- [ ] **格式统一**：反引号是否仅用于技术标识？中英文术语、大小写、箭头与列表句号是否全页统一？
