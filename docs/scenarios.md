# 典型场景

::: info 核心摘要
本页围绕场景优先级、组件组合、治理重点与验收指标，提供从首批试点到复杂自动化场景的落地判断依据。所有场景均基于正式组件清单构建，不引入额外组件。
:::

## 场景选择原则

优先落地的场景通常同时满足四项条件：

- **业务价值可量化**：目标清晰，能够通过真实业务指标衡量成效。
- **数据与权限边界明确**：涉及的数据范围清楚，权限控制规则易于定义。
- **交付周期可控**：能够在 4 到 12 周内形成可试用版本。
- **容错空间充足**：失败成本可控，支持人工兜底与逐步放量。

## 场景优先级矩阵

| 场景 | 业务价值 | 集成复杂度 | 治理敏感度 | 适合作为首批场景 |
| --- | --- | --- | --- | --- |
| 内部知识助手 | 高 | 低到中 | 中 | 是 |
| 服务台智能分诊 | 高 | 中 | 中到高 | 是 |
| 流程自动化 Agent | 中到高 | 高 | 高 | 第二批更合适 |
| 数据分析助手 | 高 | 高 | 高 | 需更严格治理后再做 |

## 场景前台形态选择

场景优先级主要由业务价值、治理风险和集成复杂度决定，而非由前台形态决定。

- **统一共享门户基线**：上述全员与多部门共享场景均基于 [AgentifUI](/components/agentifui) + 门户 / BFF / API 层交付，统一承接应用目录、工作台、会话上下文与多应用分发。
- **扩展能力边界**：面向少量高阶用户、研发或高信任小组的个人自治型超级智能体（如 [OpenClaw](/components/openclaw)）不作为第 3 层共享多用户门户，归属 [扩展升级](/extension-capabilities) 按独立沙箱多实例隔离评估。
- **下游保持收敛**：无论面向何种业务场景，下游均遵循“一条主平台路线 + 知识层 + 模型网关 + 治理链路”的收敛规则。

## 场景与组件组合速览

| 场景 | 前台形态 | 主控组件 | 知识 / 数据组件 | 模型与治理组件 |
| --- | --- | --- | --- | --- |
| 内部知识助手 | `AgentifUI` + 门户 / BFF | `Dify` / `RAGFlow` | `LlamaIndex` + `Weaviate` | `LiteLLM`、`LangFuse`、`Casbin` |
| 服务台智能分诊 | `AgentifUI` / 工单前台 + 门户 / BFF | 主平台路线 + `LangGraph` | `LlamaIndex` + `Weaviate` | `LiteLLM`、`Casbin`、`OpenTelemetry` |
| 流程自动化 Agent | `AgentifUI` + 门户 / BFF | `LangGraph` | `OpenMetadata`、`dbt Core`、`LlamaIndex` | `LiteLLM`、`Casbin`、`LangFuse` |
| 数据分析助手 | `AgentifUI` / 业务门户 | `LangGraph` | `OpenMetadata`、`dbt Core`、`PostgreSQL` | `LiteLLM`、`Casbin`、`LangFuse` |

## 场景一：内部知识助手

### 业务目标

让员工通过自然语言快速查询制度、流程、产品说明、售后知识和项目资料，减少人工查找和重复问答。

### 推荐链路

门户 / 企业 IM → `APISIX` → `AgentifUI` / 门户 BFF → 主平台路线 → `LlamaIndex` → `Weaviate` → `LiteLLM` → `vLLM`

如需更复杂的问答状态控制，可在编排层补充 `LangGraph`。

### 关键能力

- 文档同步与增量索引
- 基于部门、角色和项目的权限过滤
- 引用来源展示与回答依据留痕
- 失败问题回流为评测样本

### 治理重点

- 知识入库前完成分类分级和责任人标注。
- 在检索阶段执行权限过滤，而非仅在登录环节鉴权。
- 输出内容保留引用出处与版本来源。
- 对敏感制度、合同及客户资料施加更严格的可见范围限制。

### 验收指标

- 常见问题命中率
- 有效引用率
- 平均检索与回答时延
- 员工查询耗时下降比例

### 上线边界

适合作为第一阶段试点，但不建议初始阶段即覆盖全公司全部知识域，更稳妥的做法是先选择单一部门、单一主题或单一业务域切入。

## 场景二：服务台智能分诊

### 业务目标

对 IT、HR、财务或客户服务工单进行自动分类、初步答复和分派，减少一线重复劳动。

### 推荐链路

渠道入口 → `APISIX` → `AgentifUI` / 工单集成层 → 主平台路线或 `LangGraph` → 工单工具 → `LiteLLM`

知识回答部分仍通过 `LlamaIndex` + `Weaviate` 提供支持。

### 关键能力

- 意图识别与表单补全
- 工单系统双向集成
- 规则与模型联合判断
- 高风险动作的人机确认

### 治理重点

- 自动分派规则必须可审计、可回放。
- 误分派、误关闭、误通知需具备回滚机制。
- 写动作和外发动作必须经过工具级授权。
- 持续监控升级转人工率与误判率。

### 验收指标

- 自动分派准确率
- 首次响应时长
- 转人工率
- 工单处理总时长下降比例

### 上线边界

该类场景已从“回答问题”进入“触发动作”阶段，因此上线前必须补齐审计、授权和人工确认链路，不能仅以模型问答效果作为放行依据。

## 场景三：流程自动化 Agent

### 业务目标

将跨系统流程拆解为可观测、可中断、可恢复的任务链，例如知识发布、销售线索处理、审批前校验或交付检查。

### 推荐链路

业务入口 → `APISIX` → 门户 / `BFF` → `LangGraph` → 工具 / 外部系统 → `Casbin` → 审计与观测

标准知识平面仍可复用主平台路线，但流程主控建议由 `LangGraph` 承担。

### 关键能力

- 状态机驱动任务编排
- 节点级日志与任务回放
- 超时、重试和补偿逻辑
- 人工审批插槽

### 治理重点

- 明确每个节点的输入、输出和责任人。
- 对外部系统写入保留审批与回滚机制。
- 对超时、重复执行和部分失败建立补偿策略。
- 对跨系统流程建立全链路 Trace。

### 验收指标

- 流程成功率
- 平均处理时长
- 人工介入比例
- 失败后恢复时间

### 上线边界

不建议作为首个试点场景。更稳妥的演进顺序是先通过知识助手和服务台场景沉淀入口、知识与治理能力，再推进跨系统流程自动化。

## 场景四：数据分析助手

### 业务目标

让业务人员以自然语言查询数据、解释指标变化、辅助生成分析结论和图表摘要。

### 推荐链路

业务门户 → `APISIX` → `LangGraph` → `OpenMetadata` / `dbt Core` / `PostgreSQL` → `LiteLLM` → 结果解释

知识解释仍可结合 `LlamaIndex`，但核心风险集中在查询权限、指标口径一致性与结果正确性。

### 关键能力

- 指标口径与元数据管理
- 基于 `dbt Core` 和治理后数据层的受控查询
- 结果解释与引用依据展示
- 数据权限隔离与沙箱控制

### 治理重点

- 禁止模型绕过权限直接查询原始数据。
- 对高风险查询、全表扫描和外发数据施加限制。
- 建立人工验真和异常复核流程。
- 将“结论看似合理但实际错误”的样本纳入评测集。

### 验收指标

- 指标解释准确率
- 查询成功率
- 错误结论发现率
- 业务分析耗时下降比例

### 上线边界

该类场景的主要风险不在于“无法作答”，而在于“输出看似合理但口径或结论错误”。因此，通常不应先于权限、审计和评测基线落地。

## 推荐落地顺序

1. 内部知识助手
2. 服务台智能分诊
3. 流程自动化 Agent
4. 数据分析助手

该顺序遵循“先切入数据边界清晰、失败成本低的场景，再逐步推进动作型与高风险场景”的演进逻辑。

## 场景与能力映射

| 场景 | 主要依赖能力 | 关键组件 |
| --- | --- | --- |
| 内部知识助手 | 知识接入、检索、引用、权限过滤 | `LlamaIndex`、`Weaviate`、`LiteLLM`、`LangFuse` |
| 服务台智能分诊 | 编排、工具调用、审计、人工确认 | `Dify` / `RAGFlow`、`LangGraph`、`Casbin` |
| 流程自动化 Agent | 有状态执行、回放、补偿、审批 | `LangGraph`、`APISIX`、`Casbin`、`OpenTelemetry` |
| 数据分析助手 | 元数据治理、受控查询、结果解释 | `LangGraph`、`OpenMetadata`、`dbt Core`、`PostgreSQL`、`LiteLLM` |
