# 方案

> **适用范围**：数万人规模企业、全私有化部署、多业务线共享的平台化建设场景。

::: info 核心摘要

- **架构**：采用九层解耦设计，统一收敛入口网关、门户工作台、主平台中枢、数据与知识底座、模型网关及双层观测治理。

## 方案定位

本方案定位于**企业级智能体平台底座**，而非单一业务应用。通过沉淀统一的模型、数据、知识、编排、门户与治理能力，支撑多部门、多场景在受控边界内持续复用。

核心建设目标包括六个方面：

- **模型统一纳管**：收敛模型接入与推理服务，解除业务系统与底层模型的直接耦合。
- **数据治理前置**：统一结构化与非结构化数据的治理链路，形成面向 AI 的标准化数据供给。
- **知识受控检索**：统一知识接入、索引构建、重排与权限控制机制。
- **编排能力收敛**：统一 Agent 编排与工具调用框架。
- **门户独立解耦**：提供统一门户、应用发布与用户交互体验。
- **治理与观测内建**：将审计、评测、监控、权限与安全治理融入全链路。

## 设计原则

以下十项原则用于确立架构约束基线，避免平台演进过程中出现组件无序叠加与边界失控：

1. **唯一模型入口**：所有模型调用统一经由 `LiteLLM`，禁止业务系统直连推理服务。
2. **数据先治后用**：结构化与非结构化数据须先进入统一数据治理层，再供给 RAG、搜索、查询与 Agent 消费。
3. **知识平面收敛**：所有知识接入与检索统一收敛至企业知识平面。
4. **主平台单轨收敛**：主平台中枢在 `Dify` 与 `RAGFlow` 中二选一，不长期并行建设多套主底座。
5. **定制运行时专责**：`LangGraph` 负责复杂定制场景与有状态长链路编排；简单调用优先采用原生 SDK，`LangChain` 仅作为其下的条件生态适配与连接器工具包。
6. **知识工程专责**：`LlamaIndex` 负责知识工程、检索编排与复杂 RAG 能力。
7. **长期记忆按需引入**：`Mem0` 仅作为条件引入的可插拔长期记忆层（与 `LangGraph` + `PostgreSQL` Checkpointer 互补），不作为全平台默认强依赖组件。
8. **双协议互操作**：协议层采用 `MCP` + `A2A` 组合，分别承载 Agent-to-Tool 与 Agent-to-Agent 互操作。
9. **门户层解耦**：门户层独立建设，不与模型层、RAG 层或编排层强耦合。
10. **治理默认内建**：安全、审计、权限与评测从首期建设即纳入主链路，不作事后补丁。

## 总体架构

平台采用**九层解耦架构**，自上而下依次为：

1. 用户与渠道层
2. 统一接入与流量治理层
3. 门户与应用层
4. Agent 编排层
5. 数据治理层
6. 知识与检索层
7. 模型网关与推理层
8. 治理与观测层
9. 基础设施层

标准请求主链路如下：

`用户 / 系统入口 → APISIX → 门户工作台 / BFF → Agent / Workflow 编排 → agentgateway（按需） → MCP / A2A / 远程 Agent / 工具 → LiteLLM → vLLM / SGLang / Qwen`

### 1. 推理层

- **`vLLM`**（通用高吞吐默认）
  - **职责**：作为通用高吞吐默认推理引擎，统一承载大模型推理服务，负责模型加载、GPU 调度、并发推理与吞吐优化。
  - **边界**：不直接暴露给业务系统，不承载权限、审计与业务逻辑。
- **`SGLang`**（条件引入 / 优选）
  - **职责**：面向多步 Agent 推理、工具调用循环与代码生成等高前缀复用负载，通过 `RadixAttention` 实现前缀 KV-Cache 复用，降低首字时延并提升有效吞吐；详情见 [SGLang](/components/sglang)。
  - **边界**：作为条件优选推理引擎与 `vLLM` 按模型池分工，统一挂接在 `LiteLLM` 之后，不直接暴露给业务系统，不承载权限、审计与业务逻辑。
- **模型组合**
  - `Qwen3.5 27B FP8`：企业通用主模型，承担问答、总结、分析与流程理解。
  - `Qwen3-Coder-Next`：承担研发助手、SQL / 脚本生成与代码类任务。
  - `Qwen/Qwen3-Embedding-8B`：提供统一向量化能力。
  - `Qwen/Qwen3-Reranker-8B`：提供统一检索重排能力。
  - `Qwen3Guard-Stream-8B`：承担输入输出安全审查、越权请求检测与内容风险识别。

### 2. 模型网关层

- **`LiteLLM`**（唯一模型入口）
  - **职责**：提供统一 OpenAI 兼容接口，承接模型路由、配额与限流、故障切换、请求日志与成本统计，面向上层屏蔽底层模型差异。
  - **边界**：不做复杂业务编排，不持有知识库。

### 3. 统一接入与流量治理层

- **`APISIX`**
  - **职责**：作为统一北向入口，承载门户、BFF、知识服务、Agent 服务和运维接口的流量接入；提供路由转发、限流、熔断、灰度、审计与插件化治理能力；与企业 `SSO / IAM` 协同承担入口级认证接入与安全前置。
  - **边界**：不替代 `LiteLLM` 的模型路由与治理；不替代 `Casbin` / `OpenFGA` 的细粒度授权裁决；不承载业务工作流编排与知识索引逻辑。
- **`agentgateway`**
  - **职责**：作为内部 AI 原生协议网关，承接 `MCP`、`A2A` 及相关南向（Southbound）协议接入；提供统一的协议路由、认证、授权与可观测边界；在复杂场景下承接 `OpenAPI → MCP` 适配、远程 Agent 接入与内部 LLM 协议治理。
  - **边界**：不替代 `APISIX` 的北向入口职责；不替代 `LiteLLM` 的默认模型治理中心角色；不承载业务应用目录与门户统一语义。

### 4. 编排层

- **`Dify`**
  - **职责**：面向业务团队快速交付通用多应用、低代码 Agent、Chatflow 与 Workflow，与平台默认 `PostgreSQL + Weaviate + LangSet` 栈天然对齐，适合知识助手、服务台助手、流程助手等标准场景。
  - **边界**：不作为企业全部核心流程引擎，不独占知识底座，不承载所有复杂企业逻辑。
- **`RAGFlow`**
  - **职责**：面向深度文档解析、复杂 RAG 检索编排，或对纯 `Apache-2.0` 开源许可证有严格合规要求的场景，作为主平台路线之一承载知识密集型应用交付。
  - **边界**：不作为企业全部核心流程引擎，不与 `Dify` 长期并行建设，不替代门户层与统一控制面。
- **`LangGraph`**
  - **职责**：作为复杂流程的核心生产级 Agent Runtime，承载长时运行、有状态工作流与失败恢复，支持人工介入、基于 `PostgreSQL` Checkpointer 的持久化检查点与复杂状态控制，适合自研复杂 Agent 服务。
  - **边界**：不替代主平台中枢的低代码交付能力，不直接替代知识工程与检索层；简单模型调用可直接使用原生 SDK，无需强制套壳。
- **`LangChain`**（条件引入）
  - **职责**：作为 `LangGraph` 生态下的可选工具包与连接器适配层，在需要快速复用社区文档加载器、文本切分器或第三方工具集成时按需引入。
  - **边界**：不作为核心业务编排支柱，不替代 `LangGraph` 承担生产级状态机编排，简单调用场景不强制依赖。
- **`LlamaIndex`**
  - **职责**：面向复杂知识源的接入、索引、查询与检索编排，承载复杂 RAG、结构化数据检索与知识工程能力。
  - **边界**：作为知识工程层，不承担门户层与统一应用发布职责。
- **`Mem0`**（条件引入）
  - **职责**：作为 `Apache-2.0` 可插拔长期记忆层，承载跨会话用户画像、语义记忆抽取与个体化上下文管理，与 `LangGraph` + `PostgreSQL` Checkpointer（会话级状态持久化）形成互补。
  - **边界**：仅在需要跨会话长期记忆的场景按需启用，不替代知识库检索层，也不作为全平台所有应用的默认运行基础。

### 5. 协议与互操作层

- **`MCP`**
  - **职责**：作为 Agent-to-Tool / Context 标准协议，统一工具、资源、提示词与上下文能力接入，连接主平台、自研 Agent、知识服务与外部系统。
  - **边界**：不承担 Agent-to-Agent 协作职责，不替代主平台编排与权限治理。
- **`A2A`**
  - **职责**：作为 Agent-to-Agent 标准协议，支持跨系统、跨框架 Agent 之间的发现、协作与任务交换，适合远程 Agent 调用、跨团队能力编排与多 Agent 分工。
  - **边界**：不替代工具协议，不替代门户层与主平台控制面。

> `MCP` 与 `A2A` 为互补协议层：`MCP` 负责工具与上下文接入，`A2A` 负责远程 Agent 协作。

### 6. 数据治理层

当前数据治理层采用轻中型组合 `OpenMetadata + SeaTunnel + dbt Core + Docling`（`Apache Tika` 作为老旧 / 偏门格式与元数据预路由条件兼容项），负责将企业原始数据治理为面向 RAG、搜索、查询与 Agent 的标准数据资产和数据服务：

- **`OpenMetadata`**：承担统一数据源登记、元数据目录、标签、责任人、血缘与资产管理，作为企业 AI 数据底座的数据治理中枢。**边界**：不替代检索引擎与在线 RAG 编排。
- **`SeaTunnel`**：承担结构化与非结构化数据的批量、增量和 CDC 同步，统一源系统接入规范与同步链路。**边界**：不替代元数据治理中枢、数据目录与权限裁决。
- **`dbt Core`**：承担结构化数据的标准化建模、口径统一与治理后数据层产出，形成面向 AI 查询与分析场景的 `Curated` 数据层。**边界**：仅覆盖结构化数据建模，不替代元数据目录与非结构化知识工程。
- **`Docling`**（默认）：承担 PDF、Office、HTML 等复杂非结构化文档的版面理解、表格还原与高保真结构化解析，作为非结构化知识入治理层的默认解析入口。**边界**：不替代知识索引引擎与复杂 RAG 检索编排。
- **`Apache Tika`**（条件兼容）：保留用于老旧 / 偏门文件格式兼容抽取与轻量元数据预路由。**边界**：不替代 `Docling` 承担复杂版面文档的默认深度解析，不替代知识索引引擎。

### 7. 知识与 RAG 层

- **主平台中枢（`Dify` 或 `RAGFlow`，二选一）**
  - **职责**：承载标准化场景应用、知识接入与检索主链路，统一知识源生命周期管理、检索编排与应用发布主路径。应将其定位为企业知识与应用主平面，而非单个应用的私有知识库工具。
  - **边界**：不与其他主平台路线长期并行建设，不承担门户层全部控制面职责。
- **检索底座分层收敛策略**
  - **默认路线**：`Weaviate`（向量检索与混合检索底座）。
  - **大规模演进路线**：`Milvus`（高规模知识库与高吞吐检索阶段）。
  - **全文 / 混合检索兼容路线**：`Elasticsearch`（适配高全文检索要求或特定主平台路线）。
  - 原则上不长期并行建设 `Weaviate + Milvus + Elasticsearch` 三套主检索底座。

### 8. 门户与交互层

- **`AgentifUI`**
  - **职责**：作为企业统一 AI 门户，提供多应用入口、聊天入口、工作台、应用目录、会话交互、应用分发与反馈提交。
  - **边界**：不持有核心编排逻辑，不直接耦合底层模型；通过统一 BFF / API 层对接 `Dify`、`RAGFlow`、自研服务及协议层能力。

> 若后续门户层能力不足，演进方向仍应保持“独立自建门户壳 + 稳定 BFF 契约”，避免与底层引擎耦合。面向少量高阶用户或高信任小组的个人自治型超级智能体（如 `OpenClaw`）不纳入第 3 层共享门户基线，归入 [扩展升级](/extension-capabilities) 按独立沙箱多实例隔离评估。

### 9. 评测与观测层

- **`LangFuse`**
  - **职责**：承载 Prompt、Trace、工具调用观测、交互回放、离线评测样本管理与应用效果分析。
  - **边界**：不替代基础设施监控、日志平台与系统级可观测体系。
- **`LangSet`**（条件引入）
  - **职责**：面向需要协同构建版本化黄金测试集与持续离线回归评测的团队，承担评测数据集工程、不可变版本血缘管理与离线回归评测触发，与 `LangFuse`（在线 Trace、Prompt 观测与评分沉淀）及 `k6`（压测与容量基线）形成三段式互补。
  - **边界**：不替代 `LangFuse` 的在线观测与样本回放，不参与生产实时请求链路，也不替代基础设施级监控体系。
- **`k6`**
  - **职责**：对入口网关、门户 BFF、知识服务、Agent 服务与模型接口执行压测与容量验证，为灰度、扩容和发布前验证提供统一脚本与基线。
  - **边界**：不参与生产请求链路，不替代长期在线监控与可观测体系。

## 数据治理与基础设施收敛结果

数据治理层与基础设施层不追求全量自建，而是优先复用企业现有能力，并对平台新增组件做最小收敛：

- **优先复用企业现有能力**：身份认证复用企业现有 `SSO / IAM` 体系，密钥与证书复用企业现有 `KMS / 证书体系`，正式生产容器底座优先复用企业现有标准 `Kubernetes` 集群，对象存储优先复用企业现有 S3 兼容对象存储；上述能力均以明确集成边界为主，避免重复自建。
- **平台新增标准底座**：数据治理采用 `OpenMetadata + SeaTunnel + dbt Core + Docling` 轻中型组合（`Apache Tika` 作为老旧 / 偏门格式与元数据预路由条件兼容项）；检索底座按 `Weaviate`（默认）/ `Milvus`（大规模演进）/ `Elasticsearch`（全文与混合兼容）分层收敛；推理引擎以 `vLLM` 为通用默认，多步 Agent 与代码负载可条件优选 `SGLang`；基础与治理栈采用 `PostgreSQL`、`Valkey` / `Redis`（新建纯开源优先 `Valkey`，兼容并保留既有 `Redis`）、`SeaweedFS`（默认自建 S3 兼容对象存储）/ `RustFS`（轻量 S3 平替，按需；优先复用企业既有 S3 存储）、分阶段容器运行底座（2–8 台试点与部门验证采用 `K3s`，10–12+ 台高可用生产演进至标准 `Kubernetes` / `RKE2`——优先复用企业既有 `Kubernetes`，新建私有化或离线环境优选 `RKE2`，依托 100% 共享 K8s API / Helm / CRD 实现零重写迁移）、[Agent 执行沙箱（`Kubernetes agent-sandbox` + `gVisor` / `Kata Containers`）](/components/agent-sandbox)、`APISIX`、`agentgateway`、`LangGraph`、`Casbin`、`k6`、`MCP + A2A` 及 `OpenTelemetry + Prometheus + Grafana + Loki`；有版本化评测数据集工程与离线回归评测需求时条件引入 `LangSet`，有跨会话长期记忆需求时条件引入 `Mem0`，大规模跨系统 RAG 文档继承树 ACL 预过滤场景条件引入 `OpenFGA`（CNCF `Apache-2.0` ReBAC，复用既有 `PostgreSQL`）。
- **暂不纳入标准底座的能力**：消息总线与独立作业总线当前暂不选型，待异步任务与事件规模提升后再行评估。

| --- | --- | --- |

| | `SeaTunnel` | 统一采集与同步引擎，承载结构化与非结构化数据的批量、增量与 CDC 接入。 |

| **运行时与接入** | `LangGraph` | 生产级 Agent Runtime，承载长时运行、有状态工作流、失败恢复、检查点与人工介入能力。 |
| | `APISIX` | 统一入口网关与流量治理层，承载北向接入、路由、限流、熔断、灰度与入口审计。 |
| | `agentgateway` | 内部 AI 原生协议网关，负责 `MCP`、`A2A` 及相关南向（Southbound）协议的统一接入、路由与治理。 |
| **存储与检索** | `PostgreSQL` | 平台主数据库，承载配置、元数据、状态、权限映射、运营数据与平台后台数据。 |
| | `Valkey` / `Redis` | 运行时加速层，承载缓存、会话、短期状态、限流计数与幂等控制；新建纯开源场景优先 `Valkey`（Linux Foundation `BSD-3-Clause`，100% 协议兼容），兼容并保留企业既有 `Redis` 集群与托管实例。 |
| | `SeaweedFS` / `RustFS` | 自建 S3 兼容对象存储，承载知识原文件、用户上传附件、导出结果与文件型中间产物；优先复用企业既有 S3 存储，自建默认采用 `SeaweedFS`（`Apache-2.0`），轻量化场景按需采用 `RustFS`（`Apache-2.0`，轻量 S3 平替）。 |
| | `Weaviate` | 默认向量检索与混合检索底座，支撑企业知识库与智能体检索场景。 |
| | `Milvus` | 大规模阶段向量检索演进底座，适用于更高规模知识库、更高吞吐与更强隔离场景。 |
| | `Elasticsearch` | 全文检索与混合检索兼容项，适用于全文搜索要求较高或特定主平台配套场景。 |
| **运行、观测与授权** | `K3s` → 标准 `Kubernetes` / `RKE2` | 分阶段容器运行底座，承载门户、编排服务、观测组件与 AI 应用服务部署：2–8 台试点与部门验证采用 `K3s`，10–12+ 台企业级高可用生产平滑演进至标准 `Kubernetes` / `RKE2`（优先复用企业既有 `Kubernetes`，新建私有化或离线集群优选 `RKE2`），全程 100% 共享 K8s API / Helm / CRD 实现零重写迁移。 |
| | [Agent 执行沙箱](/components/agent-sandbox) | 基于 `Kubernetes agent-sandbox` + `gVisor`（默认）/ `Kata Containers`（裸金属 KVM 强隔离），为第 4 层不可信代码、脚本与工具执行提供强隔离运行环境。 |
| | `OpenTelemetry + Prometheus + Grafana + Loki` | 平台可观测底座，覆盖指标、日志与统一埋点标准，与 `LangFuse` 构成双层观测体系。 |
| | `LangSet`（条件引入） | 评测数据集工程与离线回归评测工具，负责可追溯的版本化测试集管理与离线回归触发，与 `LangFuse`、`k6` 互补。 |
| | `k6` | 统一压测与容量验证工具，覆盖网关、门户 BFF、知识服务、Agent 服务与模型接口。 |
| | `Casbin` | 默认轻量级嵌入式授权与策略裁决引擎，覆盖应用访问、RBAC / ABAC、工具调用权限与多租户 / 部门级授权控制。 |
| | `OpenFGA`（条件引入） | CNCF `Apache-2.0` 关系型授权（ReBAC）引擎，复用既有 `PostgreSQL`，用于大规模跨系统 RAG 文档继承树 ACL 预过滤与 `ListObjects` 下推。 |

## 分层平面视图

按能力平面归并后，平台整体由九个协同平面构成：

1. **统一接入与流量治理平面**：`APISIX` + `agentgateway`，承担北向统一入口、路由限流灰度审计，以及内部 `MCP / A2A` 等南向协议治理。
2. **模型服务平面**：`vLLM`（通用高吞吐默认）+ `SGLang`（条件优选，多步 Agent 与代码负载）+ `Qwen` 模型族 + GPU 集群调度。
3. **模型网关平面**：`LiteLLM`，承担统一 API、路由、配额、熔断与调用审计。
4. **协议与互操作平面**：`MCP` + `A2A`，承担工具接入、上下文接入与远程 Agent 协作。
5. **数据治理平面**：`OpenMetadata` + `SeaTunnel` + `dbt Core` + `Docling`（`Apache Tika` 条件兼容），承担数据源登记、采集同步、结构化治理、非结构化解析与资产发布。
6. **知识服务平面**：`Dify` / `RAGFlow` + `Qwen/Qwen3-Embedding-8B` + `Qwen/Qwen3-Reranker-8B` + `Weaviate` / `Milvus` / `Elasticsearch`，承担基于治理后资产的切片、索引、检索与权限过滤。
7. **Agent 运行与编排平面**：标准化场景采用 `Dify` / `RAGFlow`（二选一），复杂流程生产级 Runtime 采用 `LangGraph`（简单调用优先原生 SDK，`LangChain` 按需作为生态连接器工具包），知识工程采用 `LlamaIndex`，跨会话长期记忆场景按需引入 `Mem0`。
8. **门户与应用发布平面**：`AgentifUI` + 门户 / BFF / API 层 + 企业 SSO + 应用中心、应用目录、会话入口与反馈运营后台。
9. **评测、治理与验证平面**：`LangFuse` + `LangSet`（条件引入） + `k6` + `Qwen3Guard-Stream-8B` + `Casbin` + `OpenFGA`（条件引入），承担审计、在线观测、版本化离线回归评测、细粒度授权与文档继承树 ACL 预过滤、内容合规、质量回放与容量验证。

## 核心业务链路

标准请求的端到端流转链路如下：

<div class="diagram-image">
  <img src="/framework-business-flow.svg" alt="企业级智能体平台核心业务链路时序图" />
</div>

1. 用户通过门户进入目标智能应用。
2. 请求首先进入 `APISIX`，执行入口级路由、限流、审计与灰度治理。
3. `APISIX` 与企业 `SSO / IAM` 协同完成认证接入，并将请求转发至门户 BFF 或统一 API 层。
4. 门户层完成组织身份识别、应用权限校验与会话上下文初始化。
5. 编排层判断请求归属标准平台应用还是定制 Agent 服务。
6. 如需调用工具、上下文或外部资源，优先经由 `agentgateway` 承接 `MCP` 路径；涉及不可信代码、脚本或工具执行时，须落入第 9 层 Agent 执行沙箱隔离运行。
7. 如需跨 Agent 协作或远程能力编排，优先经由 `agentgateway` 承接 `A2A` 路径。
8. 如需知识增强或数据查询，优先消费数据治理层发布的 AI 数据服务与治理后数据资产。
9. 请求进入主平台的知识检索链路或受控查询链路。
10. 检索前按用户权限、部门与数据标签执行前置过滤（大规模跨系统文档继承树场景下，可由条件引入的 `OpenFGA` 执行 ReBAC ACL 预过滤）。
11. 召回结果经 `Qwen/Qwen3-Reranker-8B` 重排。
12. 编排层组织最终上下文与工具调用计划。
13. 所有模型请求统一发往 `LiteLLM`。
14. `LiteLLM` 将请求路由至对应 `vLLM`（或 `SGLang`）+ `Qwen` 模型实例。
15. 输入输出经 `Qwen3Guard-Stream-8B` 或策略引擎执行安全审查。
16. 全链路轨迹写入 `LangFuse` 与审计系统。
17. 结果返回门户，支持用户反馈、人工接管与追踪回放。

## 优先落地场景

建议从以下三类高确定性场景切入，避免初期追求全能平台建设：

| 优先场景 | 目标用户 | 典型能力 | 落地价值 |
| --- | --- | --- | --- |
| **企业知识助手** | 全员 | 制度、流程、产品文档、FAQ 与项目资料检索问答 | 价值路径最明确，适合作为首期切入点 |
| **服务台与内部支持助手** | IT / HR / 财务共享服务 | 工单分诊、标准问答、流程指引与表单补全 | 效率提升可量化，便于业务侧快速感知 |
| **研发与数据助手** | 研发、运维与数据团队 | 代码生成、SQL 辅助、日志分析与技术知识检索 | 充分发挥 `Qwen3-Coder-Next` 专业模型能力 |

## 高可用与容量建议

数万人规模企业的工程难点不在注册用户数，而在峰值并发与知识库体量。容量与高可用设计至少应满足以下基线：

- **无状态与入口层**：门户、网关、编排与知识服务均支持水平扩容；核心服务最少双实例；`APISIX` 至少双实例部署，配置与路由变更纳入版本控制。
- **有状态存储层**：`PostgreSQL` 采用主从或高可用集群；`Valkey` / `Redis` 采用哨兵或集群模式。
- **检索与数据治理隔离**：默认检索底座按 `Weaviate` 独立规划并支持扩展，大规模阶段演进至 `Milvus`，全文 / 混合兼容需求单独评估 `Elasticsearch`；离线数据治理任务与在线推理链路隔离部署。
- **GPU 推理分池**：按模型拆池，避免通用推理、代码生成与安全审查争抢算力；通用池默认采用 `vLLM`，代码与多步 Agent 推理池可条件优选 `SGLang` 以复用前缀 KV-Cache：
  - 通用推理池：`Qwen3.5 27B FP8`
  - 代码推理池：`Qwen3-Coder-Next`
  - 安全审查池：`Qwen3Guard-Stream-8B`
- **发布前容量验证**：发布前统一使用 `k6` 对入口网关、门户 BFF、知识检索链路与模型接口建立压测基线。

## 安全与治理框架

安全与治理是企业级平台可投产的必要前提，贯穿身份、数据、行为审计与发布全链路。

<div class="diagram-image">
  <img src="/framework-governance-loop.svg" alt="企业级智能体平台安全与治理控制点闭环图" />
</div>

- **身份与权限**：对接企业统一 `SSO / IAM`，入口统一收敛至 `APISIX`，遵循从小到大的授权演进路径——默认由 `Casbin` 承担轻量级嵌入式 RBAC / ABAC 与工具动作级权限裁决（覆盖应用级、知识库级、工具级与数据标签级四层权限）；当进入大规模跨系统 RAG 文档继承树 ACL 预过滤场景时，条件引入 `OpenFGA`（CNCF `Apache-2.0` ReBAC，复用既有 `PostgreSQL`）与 `Casbin` 分层协同。
- **数据安全**：落实文档入库分类分级、敏感字段脱敏、检索前权限过滤与输出前内容审查。
- **执行沙箱安全**：第 4 层 Agent 触发的不可信代码、脚本与工具执行，须统一落入第 9 层 [Agent 执行沙箱](/components/agent-sandbox)（`Kubernetes agent-sandbox` + 默认 `gVisor` / 裸金属 KVM 强隔离 `Kata Containers`），并强制落实三项安全红线——独立沙箱节点池、默认拒绝出网白名单与凭据隔离（Secret Stripping）。
- **行为审计**：全量记录用户请求、检索命中、Prompt 摘要、模型调用、工具执行、人工介入与安全命中事件。
- **发布治理**：对 Prompt、知识库与模型路由实施版本化管理；遵循“压测基线达标 → 离线评测通过 → 灰度验证 → 正式发布”的受控流程。

## 主要风险与取舍

| 潜在风险 | 应对策略 |
| --- | --- |
| **`Dify` / `RAGFlow` 职责重叠** | 按企业路线二选一，不并行建设多套主底座或主知识平面，编排与知识链路围绕单一主平台收敛。 |
| **`LangGraph` / `LangChain` / `LlamaIndex` / `Mem0` 叠加复杂度过高** | 严格收敛边界：`LangGraph` 为复杂流程核心生产级 Runtime，简单调用优先原生 SDK，`LangChain` 仅作可选生态连接器；`LlamaIndex` 负责知识工程与复杂 RAG；`Mem0` 仅在跨会话长期记忆场景按需引入，与 `LangGraph` + `PostgreSQL` Checkpointer 互补。 |
| **`MCP` 与 `A2A` 边界混淆** | `MCP` 专注 Agent-to-Tool / Context 接入，`A2A` 专注 Agent-to-Agent 协作，二者互补而不互替。 |
| **`AgentifUI` 难以承载完整企业门户** | 将其定位为起步前端壳，核心控制点下沉至自研 BFF 与统一身份层，确保前端可替换、后端契约稳定；个人自治型超级智能体（如 `OpenClaw`）归属 [扩展升级](/extension-capabilities) 独立沙箱评估，不作为第 3 层共享门户替代方案。 |
| **`LangFuse` 无法覆盖全平台运维** | `LangFuse` 专注 LLM 级观测，必须叠加基础设施级可观测性（Observability）体系形成双层观测。 |
| **基础设施过度建设** | 身份与密钥复用企业现有体系，入口收敛至 `APISIX`，消息总线与独立全文检索等非必要能力不前置建设。 |
| **数据治理层过重导致运维复杂** | 采用 `OpenMetadata + SeaTunnel + dbt Core + Docling` 轻中型组合（`Apache Tika` 仅作老旧 / 偏门格式与元数据预路由条件兼容），先满足 RAG / 搜索 / 查询 / Agent 核心数据供给，再随规模演进。 |
| **编排与检索组件全量并行** | 复杂编排以 `LangGraph` 为核心生产级 Runtime，`LangChain` 仅按需提供连接器适配；检索以 `Weaviate` 为默认，`Milvus` 为大规模演进，`Elasticsearch` 仅作兼容项。 |
| **`Elasticsearch` 许可证边界风险** | 将其严格限定为兼容项而非默认主底座；如企业对许可证边界敏感，须在正式落地前结合法务口径单独确认。 |

## 实施路线

| 阶段 | 核心目标 | 关键交付与动作 |
| --- | --- | --- |
| **阶段一：PoC** | 验证核心问答链路价值 | 搭建 `vLLM + LiteLLM + 主平台（Dify / RAGFlow） + MCP + LangFuse`；打通企业知识助手，接入 1–2 个业务部门，建立基础权限与审计。 |
| **阶段二：试点生产** | 补齐入口治理与发布门槛 | 对接企业 `SSO / IAM`；引入 `APISIX` 收敛统一入口与灰度；建统一门户入口；引入 `Qwen3Guard-Stream-8B`；建设评测集、运营看板与 `k6` 压测基线；扩展服务台场景。 |
| **阶段三：平台化** | 支撑多业务线规模复用 | 引入自研 BFF；收敛知识平面与应用发布规范；支持多业务线、多租户与多应用目录；拓展研发助手、数据助手等专业应用。 |
| **阶段四：规模化治理** | 降本增效与精细化运营 | 推进模型路由优化、成本治理、安全审查闭环、更细粒度权限与数据治理，建立常态化平台运营体系。 |

## 方案总览收敛

::: tip 一句话架构全景
- **推理与模型网关**：`vLLM`（通用高吞吐默认）+ `SGLang`（条件优选，多步 Agent 与代码负载）+ `Qwen` 模型族构成推理底座，`LiteLLM` 构成唯一模型网关。
- **入口与协议治理**：`APISIX` 构成北向统一入口网关与流量治理层，`agentgateway` 承担内部 AI 协议治理，`MCP + A2A` 构成互操作协议层。
- **数据与知识底座**：`OpenMetadata + SeaTunnel + dbt Core + Docling`（`Apache Tika` 条件兼容）构成企业 AI 数据治理底座；`Weaviate` 为默认检索底座，`Milvus` 为大规模演进，`Elasticsearch` 为全文 / 混合检索兼容项。
- **主平台与 Agent 能力**：`Dify` 或 `RAGFlow`（二选一）构成主平台中枢；`LangGraph` 构成复杂流程核心生产级 Agent Runtime（简单调用优先原生 SDK，`LangChain` 按需作为生态连接器工具包）；`LlamaIndex` 负责知识工程与复杂 RAG；`Mem0` 作为条件引入的可插拔长期记忆层。
- **门户与交互层**：`AgentifUI` + 门户 / BFF / API 层构成统一门户前台与应用发布入口。
- **运行、观测与治理**：`PostgreSQL + Valkey / Redis`（新建纯开源优先 `Valkey`，兼容并保留既有 `Redis`）`+ SeaweedFS`（默认）/ `RustFS`（轻量 S3 平替，按需；优先复用企业既有 S3 存储）`+ K3s`（2–8 台试点与部门验证）→ 标准 `Kubernetes` / `RKE2`（10–12+ 台企业级高可用生产，优先复用企业既有 `Kubernetes`，新建私有化或离线集群优选 `RKE2`，100% 共享 K8s API / Helm / CRD 零重写迁移）与 [Agent 执行沙箱（`Kubernetes agent-sandbox` + `gVisor` / `Kata Containers`）](/components/agent-sandbox) 构成运行基础设施；`LangFuse + LangSet（条件引入） + k6 + Casbin + OpenFGA（条件引入） + 平台观测体系` 构成观测评测与企业治理层。
:::
