# 1. 用户与渠道层

> 定位：承接员工、运营、业务系统与外部渠道进入智能体平台的各类访问入口。
>
> 当前承载对象：企业现有 Web、IM、工单、邮件、CRM / ERP 与 `Webhook` 入口。

## 本层定义

用户与渠道层是企业智能体系统最贴近真实使用者的交互面，负责将用户请求与外部业务事件稳定接入平台。

本层的设计重点不是新建统一前端组件，而是复用企业既有的入口体系，将访问入口、会话入口、消息入口与业务触发入口纳入统一的治理链路。

## 本层功能

- **多渠道入口承接**：承接员工门户、企业 IM、工单系统、邮件与业务系统入口。
- **多样化触发方式**：提供聊天、表单、工单发起、消息通知与 `Webhook` 回调等进入方式。
- **上下文透传**：将用户身份、组织归属、渠道标识与来源系统等上下文传递至下游接入层与应用层。
- **交互闭环回传**：将用户反馈、人工转办与会话续接等动作回传至对应的业务入口。

## 当前承载对象

本层不新增独立开源组件，主要复用企业既有能力：

- 企业 Web 门户
- 企业 IM
- 工单系统
- 邮件入口
- CRM / ERP 及其他业务系统入口
- `Webhook` 与外部系统回调入口

::: tip 设计重点
本层的核心目标是**统一接入与统一治理**，而非重复建设新的渠道平台。
:::

## 上下游关系

上游对象：

- 员工、运营、客服与管理人员
- 企业内部业务系统
- 外部系统事件与回调

下游层级：

- [统一接入与流量治理层](/layers/access-traffic-governance)
- [门户与应用层](/layers/portal-application)

默认链路应保持为：

`渠道入口 → 统一接入 → 门户 / BFF → Agent 编排`

## 边界

本层负责“接入平台”，不承担以下职责：

- **模型调用**：不直接调用模型或维护模型路由。
- **数据与知识直连**：不直接访问知识索引或原始业务数据。
- **授权裁决**：不承担细粒度授权裁决。
- **编排调度**：不承载工作流编排与工具调度逻辑。

::: warning 架构红线
严禁在渠道入口直接内嵌模型调用、数据访问或流程编排能力，避免平台退化为“多入口各自为战”的失控状态。
:::

## 关键链路

### 1. 人机交互链路

1. 用户从 Web、IM 或工单入口进入。
2. 渠道入口将身份与来源上下文传递至统一接入层。
3. 统一接入层完成认证接入、路由与前置治理。
4. 门户与应用层或 Agent 编排层继续处理业务逻辑。

### 2. 事件触发链路

1. CRM、ERP 或工单系统通过 API 或 `Webhook` 发起事件。
2. 事件优先经过统一接入层。
3. 下游平台依据既定规则触发应用、流程或通知。

## 治理要求

- **跨渠道身份映射**：同一用户在不同渠道中的身份映射必须可追踪。
- **审计上下文留痕**：渠道入口必须保留来源系统、会话标识与时间戳信息，满足审计追溯要求。
- **基础可访问性**：用户可见界面应满足基本可访问性规范，避免将关键能力局限在单一交互模式中。
- **统一入口收敛**：渠道层不得绕过统一接入层直接访问编排层、知识层或模型层。

## 部署与发布要求

- **复用既有入口**：优先复用企业现有门户、IM 与业务系统入口，避免重复建设独立入口。
- **入口流量收敛**：入口流量统一收敛至网关层，避免各渠道单独暴露后端服务。
- **契约化发布解耦**：渠道发布节奏可快于后端平台，但接口契约须通过统一 API 管理。
- **保持薄适配层**：渠道侧仅保留最薄的适配逻辑，业务流程与智能能力统一下沉至下游层级处理。

## 风险与取舍

- **直连导致治理失控**：若各渠道分别直连后端，身份体系、审计追踪与限流策略将迅速失控。
- **适配层过重推高维护成本**：若在渠道适配层沉淀过多业务逻辑，后续迁移与跨渠道复用成本将显著上升。
- **入口单一限制业务渗透**：若仅关注聊天入口而忽略工单、邮件与业务系统触发，平台将难以深入企业核心流程。
