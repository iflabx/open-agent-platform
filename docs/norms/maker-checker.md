# Maker-Checker

> 类型：人工审批与双人复核规范
>
> 采用定位：高风险动作人工复核与职责分离基线
>
> 当前口径：截至 2026-03-17，`Maker-Checker` 更准确地说是一类基于 `Separation of Duty` 与 `Dual Authorization` 的治理控制要求，而不是单一正式技术标准；在企业智能体平台中，它应被写成高风险动作的强制控制基线
>
> 权威来源：NIST 术语表中的 `separation of duties`、`dual authorization`，以及 NIST 800-53 / 800-172 所代表的控制基线思路
>
> 执行落点：门户 / BFF 的审批入口、编排层的人机协同节点、`Casbin` 的前置授权、审计与追踪链路

## 定位与价值

`Maker-Checker` 是本方案针对高风险动作的人工复核治理基线。

它要求将“发起动作的主体”与“批准动作的主体”严格分离，确保模型、工具与自动化流程即使具备执行能力，也无法在高风险场景中绕过人工确认与职责分离直接落地。

## 规范约束什么

- **复核触发范围**：明确哪些动作必须经过人工确认、双人复核或人工接管。
- **主体责任划分**：界定发起人、审批人与执行系统之间的职责边界。
- **上下文与证据要求**：明确审批前必须呈现的决策上下文，以及审批后必须留存的审计证据。
- **例外与异常处理**：规范紧急放行、失败补偿、超时处理与事后复盘机制。

## 核心原则

- **发起与批准分离**：严禁同一主体同时提出并放行高风险动作。
- **基于上下文的实质审批**：审批并非形式化的按钮确认，而须基于动作对象、上下文、影响范围与风险级别做出判断。
- **强制控制链路**：高风险动作须严格遵循“先授权 → 再审批 → 再执行 → 再留痕”的控制闭环。
- **审批全程可回溯**：审批结果须可追溯、可撤销、可复盘，不能仅保留“已通过”状态。
- **紧急旁路严控留痕**：紧急旁路仅作为例外路径存在，须配套更严格的留痕与事后审查机制。

## 在方案中的落点

- **高风险场景强制准入**：对外发送通知、写入业务数据、执行数据库变更、调用高风险工具与触发生产系统动作等场景，均须强制进入 `Maker-Checker` 流程。
- **门户与编排协同**：门户 / `BFF` 提供审批入口与状态视图，编排层或 Agent Runtime 在审批节点等待继续执行、拒绝或人工接管。
- **权限与审批叠加**：[Casbin](/components/casbin) 负责前置权限判断，但权限通过不等于可直接执行高风险动作。
- **统一审计贯通**：审批动作、审批意见、执行结果与补偿结果均纳入统一审计与追踪链路。

## 与组件 / 协议关系

- **与 [RBAC + ABAC](/norms/rbac-abac) 互补**：前者界定“谁有资格发起 / 审批”，后者界定“哪些动作必须复核”。
- **与 [Casbin](/components/casbin) 配合**：授权裁决用于确定操作资格，`Maker-Checker` 用于控制最终落地执行。
- **与 [OpenTelemetry](/standards/opentelemetry) 及平台审计链路配合**：打通审批请求、执行请求与最终结果的追踪标识。
- **与 [身份接入协议（OIDC / OAuth2 / SAML / SCIM）](/protocols/identity-access) 配合**：确保审批主体、代理主体与执行主体在身份层面可区分、可追踪。

## 适用场景

- 生产数据写入、删除与批量修改
- 外部通知、邮件、短信、工单或客户触达
- 数据库执行、脚本触发与运维动作
- 权限变更、租户变更与配置发布
- 合同、审批、资金或其他高敏业务流程

## 边界

- 不要求所有动作均执行双人复核，核心在于高风险动作的分级治理。
- 不替代授权模型、审批系统或业务流程系统本身。
- 不等同于前端仅弹出交互确认框；缺乏独立审批主体与审计留痕的确认不属于 `Maker-Checker`。
- 不应仅在人工界面层生效，必须防止 API、脚本与工具调用路径绕过审批。

## 落地规则

- **维护高风险动作目录**：先梳理并确立高风险动作目录，明确必须进入复核流程的操作边界。
- **厘清四类参与角色**：明确 `maker`、`checker`、执行者与审计责任人，避免角色混同。
- **充分展示审批上下文**：审批界面至少展示动作摘要、目标对象、影响范围、触发来源与当前上下文。
- **执行前二次校验**：动作真正执行前须再次校验审批状态、时效性与上下文是否发生变更。
- **完备异常补偿路径**：为拒绝、超时、撤回、失败与紧急旁路分别定义处理规则与补偿机制。

## 治理注意点

- **防范同人双角绕过**：防止同一人员通过多账号、代理身份或脚本路径同时扮演 `maker` 与 `checker`。
- **封堵底层旁路通道**：杜绝工具层或 API 层存在绕过审批的直接调用入口。
- **严控审批有效时效**：为审批记录设置合理有效期，避免历史审批长期悬挂后被误用。
- **贯通端到端审计证据**：将审批链路与执行链路关联至统一审计记录，确保事后可完整追溯“谁申请、谁批准、系统执行了什么”。
