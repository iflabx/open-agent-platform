# 企业智能体能力与规范体系

::: info 核心摘要
本页定义面向私有化、平台化、长期运行的企业级智能体平台**最低能力基线与架构强约束**，覆盖 11 个核心能力域与生产准入清单。

- **能力基线优先**：明确无论采用何种具体组件，企业级平台必须具备的能力完整度与治理底线。
- **强约束落地**：涵盖身份组织上下文、权限感知检索、高风险动作 `Maker-Checker` 审批、双层观测与 SRE 可恢复性。
- **核心关联**：[方案](/framework) · [总体架构](/architecture) · [协议与标准体系](/protocol-standards) · [数据治理层（企业 AI 数据底座）](/data-governance) · [组件](/components) · [开源状态与许可证说明](/open-source-status)
:::

## 能力基线定位

在整体文档体系中，组件规范、协议标准与能力基线承担不同职责：

- **组件选型视图**：明确各能力域采用的开源组件及其职责边界。
- **协议与标准视图**：明确跨层接口、互操作协议、观测语义与治理规范。
- **能力与规范基线**：明确无论采用何种实现，企业级平台最低必须具备的能力域、强约束与对应落点。

因此，本体系不以罗列组件数量为目标，而聚焦三项核心验证：

1. 能力域覆盖是否完整。
2. 架构与治理强约束是否明确。
3. 各项能力在技术选型中是否有明确落点。

## 平台达标总标准

结合 NIST AI RMF 的治理框架，企业级智能体平台至少须同时满足以下六项要求：

1. **责任归属明确**：建立清晰的治理责任链，安全、评测、发布与审计从架构初期即纳入设计，不作为事后补丁。
2. **上下文完整传递**：能够识别用户、组织、租户、数据域与动作权限，并沿调用链透传。
3. **全链路可追踪**：将知识、工具、模型与工作流纳入同一条可追踪、可回放的受控链路。
4. **高风险动作受控**：将高风险动作纳入人工确认、双人复核或人工接管机制。
5. **正式发布门槛**：将离线评测、灰度发布、回滚机制与容量验证纳入标准发布流程。
6. **平台底座复用**：支持在多业务场景间复用统一底座，避免各业务应用重复建设独立系统。

## 能力域总览

| 能力域 | 企业级最低要求 | 强约束 | 方案落点 |
| --- | --- | --- | --- |
| 治理与责任归属 | 有平台 owner、数据 owner、应用 owner、发布责任链 | 没有 owner 的能力不进入生产 | 平台团队 + 业务团队 + 数据团队 + 安全团队协作 |
| 身份与组织上下文 | 统一身份、组织属性、租户与渠道上下文 | 认证与授权分离 | 企业现有 `SSO / IAM` + `APISIX` + `Casbin` |
| 门户与应用管理 | 统一入口、应用目录、反馈闭环 | 门户不承载底层智能逻辑 | `AgentifUI` + 门户 / BFF / API 层 |
| 运行时与编排 | 多步任务、状态持久化、人工介入、失败恢复 | 高风险动作不能走无审计直写；不可信代码、脚本与工具执行须落入独立执行沙箱 | 主平台路线 + `LangGraph`（按需搭配 `LangChain` 连接器、`Mem0` 长期记忆）+ [Agent 执行沙箱](/components/agent-sandbox) |
| 工具与协议互操作 | 工具有统一接入、参数契约和调用留痕 | 协议优先于私有耦合 | `MCP`、`A2A`、`OpenAPI`、`JSON Schema` |
| 模型服务与治理 | 统一模型入口、路由、配额、留痕和回滚 | 上层不直接耦合底层推理实现 | `LiteLLM` + `vLLM`（默认）/ [SGLang](/components/sglang)（条件优选）+ `Qwen` |
| 数据治理与知识供给 | 数据先治理，再进入检索、查询和 Agent | AI 不直接连原始源系统 | `OpenMetadata`、`SeaTunnel`、`dbt Core`、`Docling`（`Apache Tika` 条件兼容）、`LlamaIndex` |
| 检索与答案质量 | 权限感知检索、引用、增量更新、失效治理 | 禁止默认将全量原文直接注入模型上下文 | `LlamaIndex` + `Weaviate` |
| 授权与动作治理 | 动作级授权、审批、人工接管、审计 | 写操作和外发动作必须可裁决 | `Casbin` + 规范页体系 |
| 观测、评测与发布 | 全链路追踪、离线评测、灰度、回滚、容量验证 | 禁止直接在生产环境手工修改关键行为配置 | `LangFuse` + `OpenTelemetry` + `k6` |
| 运行与 SRE | 多环境、备份恢复、容量规划、故障处理 | 生产环境必须可恢复；执行沙箱落实独立节点池、默认拒绝出网白名单与凭据隔离 | `K3s`、[Agent 执行沙箱](/components/agent-sandbox)（`Kubernetes agent-sandbox` + `gVisor` / `Kata Containers`）、`PostgreSQL`、`Valkey` / `Redis`、`SeaweedFS`（优先复用企业现有 S3 对象存储，轻量替代 `RustFS`） |

## 详细能力要求

### 1. 治理与责任归属

企业级平台建设的核心前提是建立清晰的责任链，而非单纯堆砌技术栈。

最低要求：

- 明确平台 owner
- 明确数据 owner
- 明确应用 owner
- 明确发布审批与回滚责任人

规范要求：

- 平台级能力与业务应用能力分离管理。
- 任何影响运行行为的配置均须明确责任人与变更记录。
- 缺乏明确责任归属的能力不得进入正式生产环境。

方案落点：[安全与治理](/governance)、[部署与发布](/deployment)、[实施路线图](/roadmap)。

### 2. 身份、组织与访问上下文

企业智能体平台不是匿名聊天系统，必须携带完整的组织与权限上下文运行。

最低要求：

- 所有用户通过企业统一身份体系进入平台。
- 用户、部门、角色、租户、渠道与应用上下文可沿完整运行链路传递。
- 认证、授权与审计形成连续闭环，而非彼此割裂。

规范要求：

- 优先对接企业现有 `OIDC / OAuth2 / SAML / SCIM` 体系。
- 认证与授权保持职责分离。
- 身份属性不得仅留存于前端会话中。

方案落点：企业现有 `SSO / IAM`、`APISIX`、`Casbin`。

### 3. 门户与应用管理

企业平台需要统一的前端入口与应用分发体系，通过 `AgentifUI` + 门户 / BFF / API 层承接全员应用目录、工作台与多应用分发，避免形成多套零散聊天界面。

最低要求：

- 具备应用目录、应用 owner、应用分组与用户反馈通道
- 提供统一入口与统一会话管理
- 明确区分公共应用、部门应用与高风险应用

规范要求：

- 门户仅负责入口承接、会话上下文聚合与应用分发。
- 核心智能逻辑不得硬编码在前端页面中，模型路由、知识治理与权限策略须保持在下游对应层级。
- 面向少量高阶用户或高信任小组的个人自治型超级智能体（如 `OpenClaw`）不纳入第 3 层共享多用户门户基线，归属 [扩展升级](/extension-capabilities) 按独立沙箱多实例隔离评估。

方案落点：`AgentifUI`、门户 / BFF / API 层。

### 4. 运行时与编排

企业级 Agent 不是“Prompt + 模型”的单步调用，而是具备持久状态与恢复能力的运行时系统。

最低要求：

- 多步任务表达能力
- 状态持久化
- 超时、重试、失败恢复与回放
- 人工确认与人工接管

规范要求：

- 高风险动作必须进入审批或双人复核模式。
- 长链路任务必须支持中断与断点恢复。
- 编排逻辑、工具 Schema 与上下文模板均须版本化管理。
- 不可信代码、脚本与工具执行必须落入第 9 层 [Agent 执行沙箱](/components/agent-sandbox)（独立沙箱节点池、默认拒绝出网白名单、凭据隔离 Secret Stripping），禁止在业务容器或共享工作节点直接运行。

方案落点：

- **标准场景**：`Dify`、`RAGFlow` 二选一
- **复杂状态流程**：`LangGraph`（核心生产级 Agent Runtime；简单调用优先原生 SDK）
- **条件生态适配与连接器**：`LangChain`（`LangGraph` 生态下的可选工具包，按需引入）
- **条件长期记忆层**：`Mem0`（`Apache-2.0` 可插拔长期记忆层，与 `LangGraph` + `PostgreSQL` Checkpointer 互补）
- **不可信执行隔离**：第 9 层 [Agent 执行沙箱](/components/agent-sandbox)（`Kubernetes agent-sandbox` + 默认 `gVisor` / 裸金属 KVM 强隔离 `Kata Containers`）

### 5. 工具与协议互操作

企业平台必须标准化解决工具接入与跨 Agent 协作两类互操作问题。

最低要求：

- 工具接入具备统一协议与接口契约
- 输入输出结构具备标准 Schema 描述
- 跨系统协作链路全程可追踪

规范要求：

- `MCP` 负责 Agent-to-Tool / Context 标准化接入。
- `A2A` 负责 Agent-to-Agent 远程协作。
- 工具参数、返回结构与校验规则必须标准化。
- 工具调用日志统一纳入全链路 Trace。

方案落点：`MCP`、`A2A`、`OpenAPI`、`JSON Schema`。

### 6. 模型服务与模型治理

模型必须作为受控基础设施统一纳管，禁止各业务应用点对点直连底层模型。

最低要求：

- 统一模型访问入口
- 路由、配额、限流与故障切换能力
- 模型版本记录与发布回滚能力
- 输入输出审计留痕

规范要求：

- 对上暴露统一兼容接口。
- 禁止上层应用直接绑定底层推理引擎实现。
- 模型切换必须经过离线评测与灰度验证。

方案落点：`LiteLLM`、`vLLM`（通用高吞吐默认）、[SGLang](/components/sglang)（多步 Agent 与代码负载条件优选）、`Qwen` 模型族。

### 7. 数据治理与知识供给

企业 AI 平台不应由各应用直接连接原始业务系统，而须先经过统一的数据治理层。

最低要求：

- 数据源统一登记
- 数据采集、清洗与标准化
- 元数据、标签、责任人与生命周期治理
- 面向 AI 的受控数据服务发布

规范要求：

- 数据至少划分为原始层、治理中间层与可消费层。
- 权限标签须贯穿至检索与查询链路。
- AI 应用优先消费经治理发布的数据服务。

方案落点：`OpenMetadata`、`SeaTunnel`、`dbt Core`、`Docling`（`Apache Tika` 作为老旧 / 偏门格式与元数据预路由条件兼容项）、`SeaweedFS`（优先复用企业现有 S3 对象存储，轻量替代 `RustFS`）、`PostgreSQL`。

### 8. 检索与答案质量

企业 RAG 的核心目标不是单纯提高召回率，而是在权限与质量约束下稳定输出可追溯的答案。

最低要求：

- 权限感知检索
- 答案来源引用
- 增量更新与失效清理
- 结果重排与质量控制

规范要求：

- 禁止默认将全量原文直接注入模型上下文。
- 回答应尽可能附带来源引用与判断依据。
- 检索质量、失效数据与坏样本须纳入持续治理闭环。

方案落点：`LlamaIndex`、`Weaviate`；大规模场景条件演进至 `Milvus`；全文 / 混合检索兼容 `Elasticsearch`。

### 9. 授权与动作治理

企业权限体系不能仅停留在静态角色表层面，必须覆盖完整动作执行链。

最低要求：

- 应用访问授权
- 知识检索授权
- 工具调用授权
- 数据域与租户隔离
- 高风险动作审批

规范要求：

- 组合使用 `RBAC + ABAC` 授权模型。
- 权限策略须版本化、可审计、可回滚。
- 人工审批与人工接管属于架构强约束，而非可选建议项。

方案落点：`Casbin`、[RBAC + ABAC](/norms/rbac-abac)、[Policy as Code](/norms/policy-as-code)、[Maker-Checker](/norms/maker-checker)。

### 10. 观测、评测与发布

企业级平台必须同时覆盖系统运行稳定性与模型输出质量两个观测维度。

最低要求：

- 统一 Trace 上下文传播语义
- 指标、日志、全链路追踪与 LLM 专项观测
- 离线评测与线上抽样复盘
- 灰度发布、回滚机制与容量验证

规范要求：

- 平台级观测与 AI 级观测缺一不可。
- 发布前必须通过离线评测、权限校验与容量验证。
- 禁止在生产环境直接手工修改关键行为配置。

方案落点：`OpenTelemetry`、`Prometheus`、`Grafana`、`Loki`、`LangFuse`、`k6`。

### 11. 运行与 SRE

一旦平台承接真实业务流量，即须具备可持续的工程运行与容灾恢复能力。

最低要求：

- `dev / staging / prod` 多环境隔离
- 备份、恢复与回滚机制
- 有状态组件的容量规划
- 关键链路故障处理预案

规范要求：

- 生产环境必须具备可验证的恢复能力。
- 持久化数据必须定期执行备份与恢复演练。
- 模型层、检索层与治理层须支持分别独立扩缩容。
- 承载第 4 层不可信代码、脚本与工具执行的沙箱须独立划分节点池，并强制落实默认拒绝出网白名单与凭据隔离（Secret Stripping）。

方案落点：`K3s`、[Agent 执行沙箱](/components/agent-sandbox)（`Kubernetes agent-sandbox` + 默认 `gVisor` / 裸金属 KVM 强隔离 `Kata Containers`）、`PostgreSQL`、`Valkey` / `Redis`、`SeaweedFS`（优先复用企业现有 S3 对象存储，轻量替代 `RustFS`）。

## 企业生产基线清单

进入正式生产前，必须逐项确认以下基线问题均已落实：

- **责任归属**：平台、数据、应用与发布各自的 owner 是否已明确。
- **身份与审计**：身份认证、动作授权与审计留痕链路是否完整贯通。
- **版本化发布**：模型、知识、工具与安全策略是否全部纳入版本与发布流程。
- **高风险兜底**：高风险动作是否配置了审批、人工确认与人工接管节点。
- **执行沙箱隔离**：不可信代码、脚本与工具执行是否已落入独立沙箱节点池，并启用默认拒绝出网白名单与凭据隔离（Secret Stripping）。
- **检索安全**：知识检索是否具备权限过滤与来源引用能力。
- **发布门槛**：上线前是否完成离线评测、灰度验证与容量基线压测。
- **容灾恢复**：生产环境是否可回滚、可恢复、可复盘。

::: tip 核心结论
企业级智能体平台的成熟度，不取决于引入组件的数量，而取决于是否将身份、数据、运行时、模型、动作、评测、发布与运维纳入同一套受控体系。
:::
