# 实施路线图

::: info 核心摘要
本页明确企业级智能体平台从试点验证到生产化中台、再到常态化运营的四阶段推进路径、组件启用节奏与阶段退出门槛。所有实施阶段均围绕正式组件清单收敛推进，不通过路线图额外引入新组件。
:::

## 总体原则

企业级智能体平台按以下顺序分阶段推进：

1. **先验证业务价值**：聚焦单一高价值场景快速形成可量化成效。
2. **再沉淀平台能力**：将试点能力标准化，复用至后续业务场景。
3. **常态化治理运营**：将治理、观测、评测与发布机制纳入日常运行体系。

该路径可有效规避两类常见偏差：

- **初期过度投入**：一开始即按“大平台”全量建设，导致周期过长、业务长期无法看到产出。
- **试点无法复用**：仅交付一次性演示原型，导致后续每个业务场景均需重建独立底座。

## 阶段总览

| 阶段 | 时间参考 | 主要目标 | 核心交付物 | 退出条件 |
| --- | --- | --- | --- | --- |
| 第一阶段 | 0 到 30 天 | 用单一高价值场景验证价值 | 试点应用、最小知识链路、最小治理链路、基础指标 | 可供真实用户试用，且具备明确验收数据 |
| 第二阶段 | 30 到 90 天 | 将试点升级为可控的生产能力 | 统一入口、权限、观测、灰度发布、第二个场景复用 | 第二个场景可复用同一底座，运行风险可控 |
| 第三阶段 | 90 到 180 天 | 形成平台化能力与组织协作机制 | 标准组件边界、发布流程、评测体系、运维基线 | 平台可承接多业务线，不依赖单点工程师经验 |
| 持续阶段 | 180 天以后 | 建立长期治理与成本优化闭环 | 评测运营、容量规划、成本路由、审计复盘 | 治理与优化进入常规运营，而非专项项目 |

## 阶段与组件启用关系

| 阶段 | 必选启用的核心组件 | 说明 |
| --- | --- | --- |
| 第一阶段 | `APISIX`、`AgentifUI`、一条主平台路线、`LlamaIndex`、`LiteLLM`、`vLLM`、`Qwen`、`PostgreSQL`、`Redis`、`MinIO`、`Weaviate`、`LangFuse` | 完成最小可试用闭环 |
| 第二阶段 | 在第一阶段基础上补齐 `Casbin`、`OpenTelemetry`、`Prometheus`、`Grafana`、`Loki`、`k6`，并引入 `LangGraph`；有版本化评测集与持续回归需求时可条件引入 `LangSet`；涉及 AI 生成代码或高敏工具执行时启用 [Agent 执行沙箱](/components/agent-sandbox)（`Kubernetes agent-sandbox` + `gVisor`），多步 Agent / 代码负载显著时可条件评估 [SGLang](/components/sglang) | 进入生产治理与复杂流程编排阶段 |
| 第三阶段 | 按需补齐 `OpenMetadata`、`SeaTunnel`、`dbt Core`、`Docling`（`Apache Tika` 条件兼容老旧 / 冷门格式与元数据预路由）全链路治理，完善独立沙箱节点池（`gVisor` / `Kata Containers` 裸金属 KVM 强隔离）与 `SGLang` 推理分池（大规模演进 PD 分离），以及条件启用 `Milvus` / `Elasticsearch` 与 `LangSet` | 进入平台化与规模化阶段 |

::: tip 门户前台与扩展能力阶段口径
全阶段第 3 层共享门户均以 [AgentifUI](/components/agentifui) + 门户 / BFF / API 层为主线，不引入第二套共享门户。面向少量高阶用户或研发团队的个人自治型超级智能体（如 [OpenClaw](/components/openclaw)）属于 [扩展升级](/extension-capabilities) 范畴，仅建议在平台治理、独立沙箱节点池与 `LiteLLM` / 审计基线完备后，按 Multi-Instance 独立沙箱隔离模式专项评估。
:::

## 第一阶段：0 到 30 天

### 目标

以最小范围跑通一个真实业务场景闭环，优先验证业务价值，避免一次性建设全部平台能力。

### 建议任务

- 选定一个高价值、低耦合、可量化的场景，优先考虑 [内部知识助手](/scenarios)。
- 选择一条主平台路线：`Dify`、`RAGFlow` 或 `Coze Studio` 三选一。
- 打通 `APISIX` → `AgentifUI` / 门户 BFF → 主平台路线 → `LiteLLM` → `vLLM` 最小链路。
- 搭建 `PostgreSQL`、`Redis`、`MinIO`、`Weaviate` 最小可用底座。
- 基于 `LlamaIndex` 建立可控的知识接入、检索与引用链路。
- 引入最小审计能力与基础 `LangFuse` 观测能力。

### 阶段交付物

- 一个可供真实用户试用的试点应用
- 一组可演示的知识问答或流程辅助用例
- 一版初始评测集与验收指标
- 一份试点边界清单，明确本阶段范围边界

### 阶段门槛

- 至少具备一组可复现的业务指标（如命中率、节省时长、工单分流率）。
- 至少打通一条完整的权限与审计链路。
- 至少有一个失败样本可完整复盘，避免仅凭经验主观调优。

### 本阶段不做

- 不同时并行两条主平台路线。
- 不为远期假设性需求一次性引入全部扩展底座。
- 不将试点期临时脚本直接作为长期生产架构。

## 第二阶段：30 到 90 天

### 目标

将单场景试点升级为可控的生产能力，并验证平台跨场景复用的可行性。

### 建议任务

- 补齐统一入口、身份透传与细粒度授权链路。
- 建立 `staging` 环境、灰度发布与回滚流程。
- 补齐 `OpenTelemetry` + `Prometheus` + `Grafana` + `Loki` + `LangFuse` 双层观测体系。
- 引入第二个业务场景并复用既有底座，不复制独立系统。
- 将高风险工具动作纳入人工确认与审计流程。
- 若涉及 AI 生成代码、不可信脚本或高敏文件处理工具执行，启用第 9 层 [Agent 执行沙箱](/components/agent-sandbox)（`Kubernetes agent-sandbox` + `gVisor`），划设专属沙箱节点池并落实默认拒绝出向白名单与凭据剥离（Secret Stripping）。
- 基于 `k6` 建立关键链路容量基线；若多步 Agent 与代码推理负载的前缀复用收益显著，可条件引入 [SGLang](/components/sglang) 与 `vLLM` 配合以降低首字延迟（TTFT）。
- 若团队需要协同构建版本化黄金测试集并建立持续回归评测，可条件引入 [LangSet](/components/langset)，与 `LangFuse` 和 `LiteLLM` 集成联动。

### 阶段交付物

- 第二个可运行业务场景
- 统一入口与标准发布流程
- 首版观测面板与异常处理预案
- 高风险动作审批与回滚机制

### 阶段门槛

- 第二个场景接入时无需新建独立底座。
- 关键链路具备可量化的容量测试数据，而非仅停留在功能演示。
- 线上异常可通过日志、追踪与审计记录快速定位。

### 本阶段不做

- 不随意新增正式组件。
- 不将各业务部门的个性化诉求演变为多套独立技术栈。
- 不将治理与评测机制延后至上线之后补齐。

## 第三阶段：90 到 180 天

### 目标

形成标准化的平台层、运维层与治理层，系统性降低跨场景复制成本。

### 建议任务

- 固化主平台路线、`LangGraph`、`LlamaIndex`、`LiteLLM`、`Casbin` 的长期职责边界。
- 补齐 `OpenMetadata` + `SeaTunnel` + `dbt Core` + `Docling` 数据治理与非结构化文档解析链路（老旧 / 冷门格式按需兼容 `Apache Tika`），建立“先治理、后检索”的数据资产发布闭环。
- 固化 [AgentifUI](/components/agentifui) + 门户 / BFF 的共享门户契约；如存在少量高阶用户或高信任小组的个人自治助手需求，再按 [扩展升级](/extension-capabilities) 专项评估独立沙箱多实例能力。
- 将知识接入、索引发布、Prompt、工具与模型路由全部纳入统一发布管理。
- 建立跨部门评测集、审计抽样与例行复盘机制；对多业务线协同维护版本化黄金测试集与持续回归评测的团队，可条件引入或扩展 [LangSet](/components/langset)，与 `LangFuse` 和 `LiteLLM` 联动形成评测闭环。
- 将入口层、检索层、模型层与治理层按负载独立扩容；模型层按场景拆分 `vLLM` 通用高吞吐池与 `SGLang` 多步 Agent / 代码推理池并视集群规模演进 PD 分离，高安全隔离场景将沙箱节点池升级为 `Kata Containers` 裸金属 KVM 强隔离。
- 根据向量数据规模与隔离需求，评估是否从 `Weaviate` 演进至 `Milvus`。

### 阶段交付物

- 平台级组件边界文档与运行基线
- 统一发布与回滚操作手册
- 评测与审计例行运营机制
- 多环境、多场景运行的容量基线数据

### 阶段门槛

- 平台可稳定支撑多业务线接入。
- 关键组件具备明确责任人与运行边界。
- 变更可受控发布，异常可按预案快速回滚。

## 持续阶段：180 天以后

### 长期演进方向

- 持续扩充领域评测集与失败样本库
- 细化模型路由、成本治理与容量规划
- 沉淀多 Agent 模板与场景复用资产
- 建立季度级审计、回顾与架构收敛机制

### 长期保持的纪律

- **治理机制常态化**：评测、观测、审计与压测须持续运行，而非仅在上线前执行一次。
- **组件清单收敛**：保持清单克制，仅在现有组件边界明显不足时评估调整。
- **双维指标联动**：平台治理指标与业务价值指标需同步评估，避免只关注单一技术指标。

## 三条持续主线

### 1. 治理主线

- 权限模型持续收敛
- 高风险动作持续纳入人工接管
- 发布前评测与审计抽样常态化

### 2. 数据主线

- 数据分类分级与责任人机制持续完善
- 知识索引质量、引用可追溯与增量更新持续优化
- 失效数据、冲突数据与重复数据持续清理

### 3. 运行主线

- 关键链路 SLO、容量基线与成本基线持续更新
- 事故复盘与回滚预案常态化演练
- 组件边界持续收敛，避免平台复杂度无序增长
